# Отношения как сумма модификаторов

Дата: 2026-10-15. Исследование #6 из `docs/MVP.md`. Веха: **M5** (дипломатия и торговля). Поверхностное; связано с ADR 0007 (формат сохранений) и ADR 0013 (`Relation` — список модификаторов).

Пометки: **[факт]** — из источника, **[предложение]** — моя прикидка, **[не подтверждено]** — источника нет.

## Краткие выводы

1. И Crusader Kings 3, и Stellaris считают отношение суммой отдельных модификаторов с причиной [S1][S2]. Игроку показывается список «причина — значение», а не одно число; то же решено у нас (столп 5, окно «Фракции»).
2. Модификаторы бывают трёх видов: постоянные, пока действует условие (в CK3 «Друг» +60, «Соперник» −60, пока связь существует) [S1]; с истечением срока (в CK3 «Напал на союзника» −25 и «Нарушил перемирие» −50 держатся по 3 года) [S1]; затухающие (в Stellaris многие штрафы помечены decaying, посол даёт +0,25 в месяц, при отзыве эффект спадает на 1 в месяц к нулю; нарушение оборонительного пакта −100 с затуханием) [S2]. CK3 пишет, что большинство модификаторов затухает к нулю [S1].
3. Stellaris отдельно хранит «доверие» (+1 к отношению за очко, потолок по умолчанию 50), оно растёт от дружественных соглашений и падает на 0,25 в месяц без источников [S2]. Это похоже на наше «накопленная дружба остаётся» (A9), но решение остаётся за владельцем.
4. Связь «дружба со злыми → минус добрым» ни CK3, ни Stellaris в таком виде не дают [не подтверждено]; в них похожий эффект идёт через союзы и общих врагов. Значит, формула наша, и её надо проверить в симуляции.
5. Для детерминизма всё целочисленное: значение в целых, затухание в целых единицах за игровой день (или в долях через счётчик тиков). Обход списка — по порядку добавления, сортировка стабильная (ADR 0005).
6. В MVP фракций две, пара — одна запись «игрок — фракция» [решено, d7: шкала на фракцию целиком]. Размер данных мал, оптимизация не нужна.

## Варианты

Формат модификатора [предложение]: `{ причина (ключ локализации), параметр (например, ID жителя), значение, вид затухания, скорость, тик создания }`. Итог = сумма, зажатая в −100…+100.

| Вопрос | Вариант | Плюсы | Минусы |
| --- | --- | --- | --- |
| Затухание | 1. Всё затухает | Просто, как в CK3 | Дружба «стирается»; сложно удержать плюс |
| | 2. Плюсы постоянные, штрафы затухают | Совпадает с вопросом A9 владельца | Можно «купить» вечную дружбу; нужен потолок |
| | 3. Вид и скорость задаёт `data/` для каждой причины | Гибко, без правок кода | Больше данных, нужны тесты баланса |
| Дружба со злыми | 1. На каждый плюс запись-«зеркало» у добрых (половина, округление к нулю) с теми же сроками | История видна в разбивке («−2: торговал с орками») | Растёт список |
| | 2. Вычисляемый член: `−сумма плюсов от злых / 2` | Не растёт список, нет рассинхрона | Нет причин по событиям; затухание привязано к чужим записям |
| | 3. Правило на уровне действия: в таблице действия сразу указаны сдвиги по обеим фракциям | Явно, настраивается в данных | Забыть строку = потерять связь |
| Подсказка | Список по убыванию модуля, одинаковые причины складываются («−10: переманил 2 жителей»), хвост — «прочее» | Читаемо | Нужен лимит строк (например, 8) |
| Хранение | Список записей в сохранении формата v3, сортировка по тику создания и ID | Просто мигрировать (ADR 0007) | Нужна верхняя граница числа записей на пару (например, 32): слияние старых в «прочее» |

## Рекомендация

Технически дёшево закладывать вариант 3 по затуханию (вид — поле причины в данных), чтобы ответ владельца на A9 сводился к правке JSON, а не кода. Связь «злые → добрые» удобнее вариантом 1 или 3: обе дают причину в подсказке. Это **предложение**, не решение: половина и округление — черновик владельца, требуют проверки симуляцией. Пока не решаем: A9 (затухание), A10 (что считать в стратегическом слое), отношения при множестве рас в v1 (матрица «каждая с каждой», ADR 0013).

Тесты: сумма без затухания; затухание за N дней точно в целых; потолок ±100; одинаковый хэш после сохранения и загрузки; подсказка содержит все записи, пока их не больше лимита.

## Когда понадобится

**M5**: переманивание (−5 за жителя), торговля (+1 за сделку), разграбление (−50), уничтожение (−80). Но формат записи нужен уже к **M4**: набеги читают итоговое число (см. `faction-raid-decision.md`).
