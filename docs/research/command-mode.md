# Режим командования

Дата: 2026-10-15. Исследование #8 из `docs/MVP.md`. Веха: **M4**. Поверхностное; связано с ADR 0004 (сущности и команды) и ADR 0005 (детерминизм).

Пометки: **[факт]** — из источника, **[предложение]** — моя прикидка, **[не подтверждено]** — источника нет.

## Краткие выводы

1. Приказ — обычная команда Core. По ADR 0005 команда исполняется на тике «текущий + 1», в реплее хранится список команд с номерами тиков. Новых механизмов для режима командования не нужно.
2. Детерминированные RTS работают так же: передаются только команды игроков, все пересчитывают одну симуляцию; команды назначаются на будущий ход [S1][S2]. Для одиночной игры задержка не нужна, достаточно +1 тик.
3. Выбор рамкой — состояние интерфейса, а не симуляции. Game превращает рамку в мировой прямоугольник и берёт бойцов из последнего снимка состояния, отсортированных по ID. В Core уходит команда уже со списком ID. Физические запросы Godot (`intersect_shape`) использовать не надо: документация не говорит о порядке и усечении результатов [S3].
4. Пауза не ломает схему: время стоит, игрок отдаёт приказы, все они получают тик «текущий + 1» и порядковый номер в рамках тика; при снятии паузы исполняются в порядке выдачи. [предложение]
5. Режимы ввода в Godot 4 удобно делать конечным автоматом в Game поверх `InputMap`-действий; геймплейный ввод ловить в `_unhandled_input`, чтобы окна UI перехватывали события раньше; `set_input_as_handled()` останавливает событие [S4].
6. Без приказа бойцы не бездельничают: у них есть режим по умолчанию (стойка), который и есть часть поведения Core. Образцы стоек (держать позицию, защита, агрессия) известны по RTS [не подтверждено ссылкой], в Stronghold есть режимы «стоять/защищать/атаковать»: в источниках не проверял.
7. Группы (Ctrl+цифра) — удобство UI; хранить их в настройках Game, не в Core. Если группа служит постоянному назначению («лучники севера»), это уже данные Core (команда `AssignPost`).

## Варианты

| Вопрос | Вариант | Плюсы | Минусы |
| --- | --- | --- | --- |
| Команды | `Move(ids, цель)`, `Attack(ids, цель)`, `Garrison(ids, участок стены)`, `SetStance(ids, стойка)` | Мало типов, тривиально записывать в реплей | Список ID в каждой команде; лимит размера |
| | Команда на группу по ID группы в Core | Короткая команда | Группы становятся состоянием Core |
| Приказ на паузе | Тик +1, порядок по номеру выдачи | Проще всего, без «режима планирования» | Игрок не видит результат до снятия паузы |
| | Режим планирования с очередью и откатом | Удобно для тактики | Лишнее состояние, отдельный интерфейс |
| Поведение без приказа | Стойка «держать пост» с радиусом привязки R тайлов: атаковать в зоне, не гнаться за пределами, вернуться | Предсказуемо, мало поиска пути | Нужны посты на стенах |
| | Стойка «автономно»: идти к ближайшему врагу | Бойцы всегда в деле | Покидают стену, ломают расстановку |
| Выбор | По рамке в экранных координатах → мировой прямоугольник → снимок | Не зависит от физики | Нужен быстрый индекс позиций в снимке |
| Ввод | Автомат режимов (Герой, Командование, Карта мира) | Явные переходы, тестируется отдельно | Нужно описать, какие действия активны в режиме |

## Рекомендация

Минимальный набор команд (четыре типа выше), выбор рамкой в Game по снимку, пауза по схеме «тик +1», по умолчанию стойка «держать пост». Это предложение; формат команд идёт в ADR 0004 после прототипа. Пока не решаем: A11 (герой в штурме, переключение «командовать / драться»), i1–i5 (раскладка кликов, A13), геймпад (по рекомендации — нет). Проверки: реплей осады с 20 приказами даёт тот же хэш; тест «приказ на паузе и снятие паузы»; пакет команд на 100 бойцов не превышает бюджет очереди путей (ADR 0003: лимит узлов на тик, порядок «приоритет, ID сущности, номер запроса»).

## Когда понадобится

**M4**: прототип выбора и приказов вместе с первым прототипом стены. Автомат режимов нужен на M2–M3 заготовкой (Герой), потому что «Карта мира» приходит в M5.
