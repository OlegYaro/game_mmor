# Данные зданий: уровни, перенос, стадии стройки (исследование #1, 15.10.2026)

Контекст: `docs/MVP.md` («Город и постройки»), `docs/ROADMAP-v1-v2.md` (п. 4, 5, 9 «Что заложить в MVP»), предложенный `docs/adr/0012-building-model.md`. Тик 10 Гц: 10 с = 100 тиков. Решения владельца (стройка ~10 с, улучшение без сноса, перенос без потерь, без износа и ремонта, один склад, снос 75%) не оспариваются. Открытые A1, A2, C6 даны вариантами.

## Краткие выводы

1. **Рекомендация: один JSON-файл на тип здания, уровни массивом внутри** (вариант 1 из ADR 0012 подтверждается). Общие поля (отпечаток, категория, размещение, арт) лежат на уровне здания, всё, что меняется с уровнем (цена, время, места, склад, рецепты, требования, прочность), лежит в `levels[]`. Сущность хранит `DefId` здания и `level`, поэтому улучшение и перенос не создают новую сущность (ADR 0004).
2. **Отпечаток общий для всех уровней.** Если уровень меняет размер, улучшение «без сноса» упирается в соседей, а перенос в проверку места. Для MVP: размер фиксирован на здание, рост размера — только через v1 с отдельным правилом.
3. **Перенос — состояние сущности, а не удаление и создание.** Это единственный способ сохранить `EntityId`, жильцов, работников, запас и очередь. Из реальных игр перенос подтверждён у Going Medieval (здание разбирается в «кучу» и ставится заново за треть времени постройки, [S1]) и у Farthest Frontier («почти бесплатно, только труд», [S3]). У Against the Storm переноса нет: только снос и постройка заново, по сообщениям игроков, не подтверждено официально [S5].
4. **Нашей ставки «без потерь» достаточно держать запас внутри сущности склада.** Склад не физический ящик, а счётчики по `DefId` предметов; перенос их не трогает, склад на время переноса недоступен (около 33 тиков).
5. **ADR 0012 нужно поправить в пяти местах** (раздел «Проверка ADR 0012»): противоречие про территорию, нет `moveTicks`, нет ограничений размещения (ровно, жила), нет формулы возврата 75%, нет состояния «улучшается».
6. **Стадии стройки не требуют ручного арта.** ArtGen может выводить 3 промежуточных кадра из финального спрайта (обрезка по высоте, доски, леса). Текущий атлас объектов (ячейка 32×32, 3 колонки) для зданий мал; нужен отдельный атлас `buildings` с укладкой «полками» как у тайлов.
7. **Время стройки задаём числом тиков в данных** (около 100 для уровня 1), независимо от A2. Формула «растёт с размером» — это просто разные числа в данных, код менять не придётся.
8. **Улучшение ставим как 100 тиков в стадии «улучшается»: здание на это время не работает, жильцы остаются.** Сна нет, поэтому «выселять на время» не нужно.
9. **Требования — список объектов с видом (`era`, `specialist`, `tech`, `race`), а не набор полей.** Новые виды добавляются данными; пустой список = нет требования.
10. **Данные Banished показывают риск при A2 = вариант (2):** строительство ждёт носильщиков с материалами [S2]; жалобы игроков на затор при нескольких стройках сразу есть в Steam-обсуждениях (не подтверждено, URL не сохранён). Вариант (1) (списать сразу) это снимает.

## Подробности

### 1. Варианты схемы данных

| Вариант | Плюсы | Минусы | Оценка |
| --- | --- | --- | --- |
| A. Один файл на здание, `levels[]` внутри | Здание читается целиком; общие поля не дублируются; валидатор проверяет монотонность уровней (места не убывают) | Файл растёт (3 уровня ≈ 60–100 строк); слияние модов (RFC 7386) заменяет массив целиком, так что мод должен переписать все уровни | **Рекомендовано** |
| B. Здание и уровень — отдельные файлы | Мелкие файлы | Ссылки `building → level`, больше перекрёстных проверок; порядок уровней приходится хранить отдельно | Не нужно при 1–3 уровнях |
| C. Уровни — отдельные здания (`house_1`, `house_2`) | Нет нового понятия | Улучшение = замена сущности: сменится `EntityId`, придётся копировать жильцов, склад, очередь; ломает FR-BUILD-06 и «перенос без потерь» | Отклонено |

Про моды: в ADR 0008 слияние идёт по RFC 7386, а он заменяет массивы целиком. Для v2 это нормально, но нужно записать в ADR 0012, иначе мод «+1 место на 2-м уровне дома» придётся делать копией файла.

### 2. Черновик схемы (единицы)

Время — тики (10 = 1 с). Расстояния и размеры — тайлы. Доли — промилле (1000 = 100%). Деньги и ресурсы — целые. Никаких `float`. Схема генерируется из C#-типов (ADR 0008), так что ниже поля будущих `record`.

```json
{
  "$schema": "../schema/buildings.schema.json",
  "buildings": [
    {
      "id": "house",
      "category": "housing",
      "footprint": { "w": 2, "h": 2, "rotatable": true },
      "placement": { "flatOnly": true, "outsideTerritory": false, "onDeposit": null },
      "art": "house",
      "levels": [
        { "buildTicks": 100,

          "requires": [ { "kind": "era", "value": "camp" } ],
          "capacity": { "residents": 2 }, "combatHealth": 200 },
        { "buildTicks": 100,
          "cost": [ { "item": "wood", "amount": 30 }, { "item": "stone", "amount": 10 } ],
          "requires": [ { "kind": "era", "value": "village" } ],
          "capacity": { "residents": 4 }, "combatHealth": 400 },
        { "buildTicks": 120,
          "cost": [ { "item": "plank", "amount": 30 }, { "item": "stone", "amount": 20 } ],
          "requires": [ { "kind": "era", "value": "city" } ],

    {

        { "buildTicks": 100,

                        { "kind": "specialist", "value": "blacksmith", "minTier": 1 } ],
          "workSlots": 1,
          "recipes": [
            { "id": "sword_t1", "inputs": [ { "item": "ingot", "amount": 2 } ],
              "outputs": [ { "item": "sword", "amount": 1 } ],

                        { "kind": "specialist", "value": "blacksmith", "minTier": 2 } ],
          "workSlots": 2,
          "recipes": [ "...sword_t1 и sword_t2, броня..." ],
          "combatHealth": 500 }
      ]
    }

```

Решения по полям:

- `cost` — массив пар, не словарь: порядок фиксирован (детерминизм и стабильный хэш). Стоимость уровня N — **только приращение** (доплата за улучшение); полная стоимость = сумма. Это даёт и возврат при сносе, и совпадение с Against the Storm, где при сносе возвращается базовая цена, а вложенное в улучшения не возвращается (сообщение игроков, не подтверждено) [S5]. У нас решено 75%, считаем от суммы уплаченных стоимостей всех достигнутых уровней, округление вниз по каждому ресурсу.
- `requires[]` — объекты `{kind, value, ...}`. Виды MVP: `era`, `specialist`. Резерв v1: `tech`, `race`. Эпоха — порядковое число в данных эпох, сравнение `>=`.
- Специалист двух видов: на уровне здания (чтобы вообще построить: игра не даёт строить кузницу 2-го уровня, пока нет кузнеца 2-го тира — так серые кнопки в меню получают причину, i4 из MVP) и на уровне рецепта (чтобы работать). Без специалиста здание простаивает, причина в инспекторе.
- `placement.outsideTerritory` — флаг ROADMAP п. 4. `onDeposit` — вид жилы (`"ore"`), нужен руднику («ставится на жилу», MVP) и полю; без этого поля рудник придётся делать особым случаем в коде.
- `footprint.rotatable` — отпечаток без поворота проще для арта; поворот меняет `w`/`h` местами.
- `art` — ссылка на группу кадров (раздел 5), а не поле каждого уровня: стадии выводятся автоматически.
- `capacity.residents` не убывает с уровнем: валидатор проверяет. `combatHealth` — целое, хранится как текущее значение в сущности (C6).

### 3. Проверка ADR 0012

1. «Перенос за пределы территории запрещён» и флаг `outsideTerritory` без правила, как они сочетаются. Правило: цель проверяется по `placement.outsideTerritory` данного здания; здания с флагом не привязаны к радиусу, остальные — по A1.
2. «Рабочие переназначаются» при переносе вне радиуса: в MVP рабочие живут в обычных домах и назначаются на здание, а не на место, перенос назначения не меняет. Фразу убрать.
3. Нет `moveTicks`: нужно число в данных (ниже).
4. Нет состояний: у сущности должны быть `Active`, `Constructing`, `Upgrading`, `Moving`, иначе в сохранении и в UI нечем различать (ADR 0007: версию формата поднять).
5. Нет формулы возврата 75% и поведения при полном складе (рекомендация: лишнее теряется, с сообщением).
6. `stageArt` в уровне избыточен: стадии одинаковы для всех уровней, выводятся из `art`.

### 4. Что происходит при переносе

Рекомендованный механизм: команда `MoveBuilding(id, newPos, rot)` проверяется в Core в начале тика; при успехе сущность переходит в `Moving` на `moveTicks` (рекомендую `buildTicks / 3`, как у Going Medieval: переустановка занимает треть времени постройки [S1]; для дома 33 тика), затем появляется на новой позиции со стадийным кадром. Старый отпечаток освобождается сразу, новый резервируется сразу (иначе два переноса займут одно место).

| Содержимое | Что делаем | Граничные случаи |
| --- | --- | --- |
| Жильцы | Остаются жильцами (`homeId` — `EntityId`, не позиция). Сна нет, никто «внутри» не сидит. После переноса идут по новому пути | Дом переносится далеко от работы: только путь длиннее, это цена игрока. Число мест не меняется |
| Работники | Назначение сохраняется. На время `Moving` слот не работает, задача снимается и возвращается на доску | Груз в руках: цель задачи — `EntityId`, а не координаты, поэтому носильщик донесёт на новое место после переноса. Резервы целей на здании снимаются и выставляются заново |
| Склад с запасом | Счётчики запаса остаются в сущности склада, ничего не пересчитывается. На время `Moving` склад недоступен для задач (ресурсы «в пути») | Склад один: на ~3 с встают все задачи с ресурсами. Альтернатива — не отключать склад, а брать цену времени (спорно, см. вопрос Q2). Переносимый склад нельзя сносить |
| Очередь производства | Прогресс текущего цикла (в тиках) хранится и замирает; очередь остаётся | Входы, уже взятые из склада, остаются во входном буфере здания |
| Стройка в процессе | Перенос запрещён. Можно отменить: возврат 100% (материалы списаны при постановке, ADR 0012) и поставить заново | Улучшение в процессе (`Upgrading`) тоже запрещает перенос |
| Здание под атакой / в зоне осады | Перенос запрещён, пока в радиусе боя есть враги; стены, ворота, башни — запрещён во время тревоги | Тревога без врагов рядом: разрешить для не оборонных зданий. Стена как «поверхность» (ROADMAP п. 7) вообще не переносится, только сносится |
| Цель вне территории | Допустимо только при `outsideTerritory: true`. Остальные — по A1 (ниже) | Граница: проверка по всему отпечатку, а не по центру |
| Цель занята | Подсветка красным, команда отклоняется, ничего не меняется. Занятость: другое здание, ресурс, вода, неровность (B2) | Резервы других переносов учитываются. Перенос «на себя же» с поворотом разрешён |
| Перенос во время тревоги | См. «под атакой». Если игроку нужно срочно — снос возвращает 75% | Это единственный законный путь «потери» при тревоге, не баг |

**A1 (ограничивать ли территорию радиусом).** Варианты и последствия для переноса: (1) радиус по эпохе: проверка `distance(center, newPos) <= radius`, перенос за радиус запрещён, при росте эпохи радиус растёт, но «выпавшие» после смены (если радиус когда-то уменьшится) здания остаются; (2) радиуса нет, запрет только у чужих поселений: перенос проверяет расстояние до чужих центров и стен; (3) радиус растёт от зданий: перенос может уменьшить территорию, поэтому нужна проверка «не оставит ли перенос соседние здания вне границы» или правило «территория не сжимается». В схеме от выбора ничего не зависит, кроме проверки в Core, поэтому решать можно после M2.

### 5. Стадия стройки в ArtGen

Проверено по коду `tools/ArtGen`: объектный атлас — 32×32 на ячейку, 3 колонки, `Origin (16, 24)`; тайл 32×16; кадры идут в `data/art/atlas.json` с `kind` `tile` или `object`. Здание 2×2 на изометрической сетке 32×16 имеет ромб основания 64×32 пикселя плюс высота, так что кадр ≥ 64×64. Нужен отдельный атлас `buildings` с переменным размером ячейки и укладкой полками (как для тайлов), `kind: "building"`.

Предложение: **четыре кадра на уровень здания, три из них выводятся из финального.** Доля прогресса в промилле (целое):

| Стадия | Прогресс, ‰ | Рисунок (выводится из кадра `lN`) |
| --- | --- | --- |
| `s0` | 0–249 | Разметка на земле и тент: ромб основания + 4 колышка, полупрозрачный силуэт |
| `s1` | 250–499 | Нижняя 1/3 силуэта + доски, сложенные рядом |
| `s2` | 500–799 | Нижняя 2/3 + леса (диагональные линии и вертикальные стойки по контуру) |
| `lN` | 800–1000 | Финальный спрайт; поверх до 1000 — тонкие леса, затем пропадают |

Количество: 13 зданий из списка MVP, в среднем 2 уровня → ~26 финальных + 78 производных = ~104 кадра. Если размер ячейки в среднем 64×64, это около 430 КБ несжатых пикселей RGBA, т. е. атлас ~1024×512, нет проблем. Чтобы не плодить кадры, можно хранить только `s0` общим для размеров (`site_2x2`, `site_3x2`…) — тогда экономия около 26 кадров. Выбор оставляю разработчику ArtGen.

Для **улучшения** `Upgrading` использовать тот же механизм с кадрами **предыдущего** уровня и лесами (Manor Lords при улучшении участка тоже показывает фазу стройки, после чего дом становится выше [S6]). Для **переноса** — только `s0` на новом месте и леса по финальному кадру.

Прогресс строится в тиках `elapsed * 1000 / buildTicks`, целочисленно; кадр выбирает Game, Core лишь отдаёт `progressPermille` в снимке.

### 6. Как улучшение меняет жильцов и производство

- **Жильцы**: остаются. Новые места появляются после завершения; заселяются обычным утренним приходом странников (MVP). Мест не убавляется никогда, поэтому выселять не нужно.
- **Производство**: на время `Upgrading` (100–150 тиков) здание стоит, прогресс цикла замирает и продолжается после. Новые рецепты открываются сразу после окончания. Слоты работников растут: свободные слоты заполняет доска задач.
- **Склад**: `storage` растёт с уровнем, запас не меняется.
- **Специалист**: улучшение с `requires.specialist` недоступно без него (серая кнопка с причиной). Иначе вложенные ресурсы лежат без пользы, как у кузницы 2-го уровня без кузнеца.
- **Уровень оружия жителей** равен уровню кузницы (MVP, b2): значит, у кузницы `outputs` задаёт тир, а не код.
- **Заимствования**: у Farthest Frontier дома улучшаются сами при выполнении привлекательности и наличии ресурсов, отключаемо переключателем [S3]; у Foundation дом может «откатиться» на уровень ниже, если условия не выполнены, но не сразу [S7]. У нас откатов нет (решение «без износа»), поэтому всё условие проверяется только при начале улучшения.

### 7. Что заложить под v1/v2

- `requires.kind`: `tech`, `race` (раса — id файла расы, ROADMAP п. 1). Значение пустого списка = без требований.
- `placement.outsideTerritory` и `onDeposit`: аванпосты и дальние рудники (v2).
- Принадлежность: у сущности здания `settlementId` (ROADMAP п. 5): захват аванпоста меняет владельца, не данные.
- `neighborBonus: []` (v1): правила вида «кузница рядом с плавильней: +N‰ скорости»; пока пустой массив. В Farthest Frontier соседство работает как «привлекательность» [S3].
- `garrison` и `upkeep` (потребление со склада по ROADMAP п. 9): потребление дров, содержание аванпоста — список пар `item/amount/periodTicks`.
- `weaponTier`/`outputTier` вместо номера уровня в коде.
- `wall`/`gate` как `category: "defense"` с `walkable: true` на отпечатке (ROADMAP п. 7).
- Миграция сохранений (ADR 0007): хранить `buildingDefId`, `level`, `state`, `stateTicks`, позицию, поворот; на удалённый уровень в данных — безопасное падение на последний.

### 8. Новые открытые вопросы к владельцу

- **Q1.** Сколько стоит перенос по времени: 0 (мгновенно), треть стройки (рекомендация) или полная?
- **Q2.** Склад на время переноса недоступен (рекомендация) или переносится мгновенно?
- **Q3.** Сколько можно сносить: совсем нельзя снести последний склад и центр?
- **Q4.** Снос 75% считается от суммы всех уровней (рекомендация) или только от последнего?
- **Q5.** Что делать с лишним при сносе, если склад полон: потерять (рекомендация) или оставить кучей на земле?
- **Q6.** Размер здания меняется с уровнем? (Рекомендация: нет.)
- **Q7.** **A2** (носильщики и строители при стройке 10 с): (1) списать материалы сразу и ждать 10 с: просто, профессии не нужны, поле `buildTicks` — единственная зависимость; (2) носить материалы и потом строить, как в Banished [S2]: естественнее, но затор при нескольких стройках и нужны строители; (3) время растёт с размером: только числа в данных. Схема выдерживает любой вариант, меняется только Core.
- **Q8.** **C6** (восстановление прочности после боя): (1) мгновенно после тревоги; (2) линейно со временем, `combatHealth` растёт на N за период; (3) бесплатно и вручную от жителей-строителей (возвращает ремонт, которого у нас «нет»); (4) только улучшением/пересборкой. Для данных нужно только поле `regenPerMinute` или его отсутствие.
