# 0010. Отрисовка карты и заглушечный арт

Статус: принято
Дата: 2026-10-14
Требования: FR-WORLD-06, FR-WORLD-12, FR-WORLD-13, FR-UI-05, NFR-01; §3 GDD (изометрия 2:1, тайлы 64×32, высоты 0–3)

## Контекст

Карта 512² в MVP и до 2048² позже, чанки 32×32, 100 жителей и 300 существ, цель 60 FPS. Арт — процедурные заглушки, которые позже заменяются без правки логики. Подробности и источники: `docs/research/isometric-rendering.md`.

Ключевые факты:
- В Godot 4.7 используется только `TileMapLayer`, старый `TileMap` устарел.
- При включённой Y-сортировке движок заводит отдельный элемент отрисовки на каждый ряд. Любой `SetCell` перерисовывает ряд и пересчитывает порядок во всём слое. На одном слое 500–700² это даёт миллисекунды на изменение тайла и падение FPS.
- Пакетного API для тайлов нет, но изменения и так собираются до конца кадра.
- `MultiMeshInstance2D` не сортируется по Y вместе с тайлами.

## Варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Один `TileMapLayer` на весь мир | Проще всего | Стоимость Y-сортировки растёт с числом рядов; медленные правки тайлов |
| `TileMapLayer` на чанк 32×32, создаются и удаляются вокруг камеры | Правка тайла дёшево; память по видимой области; совет мейнтейнера Godot | Нужен менеджер чанков и стыки сортировки между чанками |
| Своя отрисовка через `RenderingServer` | Полный контроль | Тот же примитив, что внутри TileMapLayer; больше кода без выигрыша по замерам |

## Решение

- **Карта:** по два `TileMapLayer` на чанк. Плоский слой «земля» без Y-сортировки. Слой «объекты» с Y-сортировкой: деревья, стены, постройки. Ячейки в абсолютных координатах мира. Физика, навигация и окклюзия у слоёв выключены.
- **Сортировка:** все слои «объекты» и спрайты существ — дети одного узла с Y-сортировкой, поэтому существа корректно заходят за стены и деревья соседних чанков.
- **Видимые чанки:** создаются вокруг камеры с запасом в один чанк, дальние освобождаются в пул.
- **Высоты 0–3:** смещение текстуры тайла вверх на 16 px за ступень через `TextureOrigin`, отдельная альтернатива тайла на каждую высоту.
- **Раскладка:** `TileShape = Isometric`, `TileLayout = DiamondDown`. Тогда преобразование координат линейное, и Core считает его сам: центр тайла `px = 32(x − y) + 32`, `py = 16(x + y) + 16`; обратное преобразование линейное с округлением. Формула проверяется тестом против `TileMapLayer.MapToLocal` в smoke-тесте M1.
- **Существа:** обычные `Sprite2D`, позиция интерполируется между двумя последними снимками Core.
- **Туман войны:** полноэкранный шейдер с маской-текстурой, один тексель на тайл, обновление только при изменении.
- **Миникарта:** отдельная текстура, один пиксель на тайл, обновляется по изменённым чанкам.
- **Заглушечный арт:** скрипт в `tools/` генерирует PNG-атлас: ромбы тайлов по биомам, силуэты с подписями для существ и построек. `TileSet` собирается из атласа в коде по таблице «ID контента → ячейка атласа» в `data/`. Замена на настоящий арт — замена PNG и таблицы, без правки логики.

## Последствия

- Цифры производительности в исследовании взяты с форумов и из issue, официальных бенчмарков нет. Бенчмарк прокрутки карты 512² ставится в приёмку M1; дополнительно делаем замер на 2048², чтобы риск v1 был виден заранее.
- Стыки сортировки между чанками проверяются визуально на тестовой сцене в M1.
- Если отрисовка через `TileMapLayer` не даст 60 FPS, запасной путь — свои элементы через `RenderingServer` с группировкой по чанку.
